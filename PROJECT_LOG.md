# Project log

A running record of decisions, problems and fixes during the build. Only things
that actually happened are in here.

---

## Phase 0 - Environment

- `node -v` → **v20.13.1**, npm 10.9.0. `git` present. **`gh`, `vercel` and the
  Supabase CLI were all absent**, which shaped two later decisions (schema
  applied by pasting SQL rather than `supabase db push`, and types maintained by
  hand rather than generated).
- `npm install` printed `EBADENGINE` for `eslint-visitor-keys@5.0.1`, which wants
  Node `^20.19.0`. ESLint runs correctly anyway, so this was noted and left
  alone rather than forcing a Node upgrade mid-build.
- `npm audit` reports **5 high-severity advisories, all dev-only**:
  `braces` → `micromatch` → `fast-glob` → `@next/eslint-plugin-next` →
  `eslint-config-next`. The only offered fix downgrades `eslint-config-next` to
  v14, which does not support Next 16. Nothing in that chain ships to
  production, so the advisories were accepted rather than breaking the toolchain.
- Working directory was empty, so the project was created as `talentflow-ats/`
  inside it.

## Phase 1 - Scaffolding and Next.js 16 surprises

`create-next-app@latest` produced **Next.js 16.4.0 / React 19.3.0 / Tailwind
CSS 4**, which differs from Next 15 in ways that mattered:

1. **`cacheComponents: true` was on by default.** Every page in this app reads
   cookies (auth) and is request-scoped, so component-level caching buys nothing
   and complicates cookie access. **Disabled it.** Confirmed afterwards from the
   build output that all routes are `ƒ (Dynamic)`, which is correct here.
2. **`middleware.ts` is deprecated in favour of `proxy.ts`.** Rather than guess,
   I read `node_modules/next/dist/build/index.js`: it throws if both files exist
   and warns that "the `middleware` file convention is deprecated". Went with
   `src/proxy.ts`. Also confirmed in
   `build/analysis/get-page-static-info.js` that proxy always runs on the
   Node.js runtime, so no `runtime` export is allowed there.
3. **Typed route props.** `PageProps<"/jobs/[id]">` and `LayoutProps<"/">` are
   globals generated by `next typegen`. Used throughout instead of hand-written
   prop types.

A baseline `npm run lint` and `npm run build` were run on the untouched
scaffold before writing any app code, so later failures could be attributed to
my changes rather than to the toolchain.

## Phase 2 - Tooling friction

- **Large SQL files could not be written through the shell.** A quoted heredoc
  containing the schema failed with `unexpected EOF while looking for matching
  '` and created nothing. Switched to direct file writes for anything large or
  quote-heavy; the shell is still used for everything else.

## Phase 3 - Schema and RLS

- **Composite foreign keys instead of a trigger.** The constraint "an
  application's candidate and job must be in the same organization as the
  application" is usually done with a trigger. Adding
  `unique (organization_id, id)` to `jobs` and `candidates` makes it a plain
  declarative foreign key on `(organization_id, candidate_id)` and
  `(organization_id, job_id)`. A cross-tenant application is now rejected by the
  database itself, with no procedural code to get wrong.
- **RLS helper functions are `SECURITY DEFINER`.** `tf_role()`, `tf_org_id()` and
  `tf_is_admin()` read `profiles`. Without `SECURITY DEFINER`, a policy *on*
  `profiles` that calls them would recurse. This is the known Supabase pattern
  and the reason the functions exist at all instead of inlining a subquery.
- **Every policy is `to authenticated`.** The `anon` role has no policy anywhere,
  so an unauthenticated PostgREST call gets nothing rather than relying on the
  app to block it.
- **`WITH CHECK` on INSERT and UPDATE is the anti-spoofing control.**
  `organization_id` is a writable column, so without `WITH CHECK` a customer
  could insert a row stamped with another tenant's id. This is tested for real
  by `scripts/verify-isolation.ts`.
- **Email/LinkedIn check constraints use `LIKE`/`ILIKE`, not regex.** The first
  draft used `~*` with a character class containing `\s`, which is awkward to
  keep correct across tooling. Shape checking at the database level is a
  backstop; Zod does the real validation.

## Phase 4 - Data access decision

The hand-written `Database` type has `Relationships: []`, which means
supabase-js cannot type-check PostgREST embedded selects
(`select("*, candidate:candidates(...)")`). Two options:

1. Hand-write the `Relationships` tuples so embedding type-checks.
2. Run two or three bulk queries and join in memory.

Chose **(2)**. The composite foreign keys make embedding ambiguous enough to
need explicit FK hints, and at MVP scale three indexed queries are
inconsequential. This is documented as a trade-off rather than hidden - it is
the first thing I would revisit at larger scale, together with generated types.

## Phase 5 - Build failures and fixes

### `lucide-react` v1 dropped brand icons

```
./src/components/pipeline/pipeline-board.tsx:13:1
Error: Export Linkedin doesn't exist in target module
Did you mean to import Link?
```

`lucide-react@1.x` no longer ships brand marks, and LinkedIn is central to the
candidate profile requirement. Wrote a small inline-SVG `LinkedInIcon` in
`src/components/ui/icons.tsx` and replaced the four usages. Also verified the
other 32 icon names against the installed package before rebuilding, rather than
fixing them one failure at a time.

### Two bugs in the drag-and-drop board, found by review before shipping

1. `useDraggable`'s `setNodeRef` was attached to **both** the card `<div>` and the
   drag handle `<button>`. Fixed to `setNodeRef` on the card and
   `setActivatorNodeRef` on the handle, so only the handle starts a drag and the
   links and dropdown inside the card stay clickable.
2. The card reused the `StageSelect` component *and* passed an `onChanged`
   callback into the board's `move()`. Both call the server action, so a single
   stage change **fired the update twice**. Replaced it with one plain
   controlled `<select>` on the card that calls the board's single `onMove`, so
   drag and dropdown share exactly one code path to the server.

### ESLint: `react-hooks/set-state-in-effect` (4 errors)

Next 16's config enables the new React Compiler-era hook rules. Four places
called `setState` synchronously inside `useEffect`. Fixed each properly rather
than disabling the rule:

| Location | Fix |
| --- | --- |
| `app-shell.tsx` - close mobile drawer on navigation | Close it in the link's `onClick` instead of reacting to a `pathname` change |
| `candidate-search.tsx` - clear the spinner when the URL settled | `useTransition` around `router.replace`, so `isPending` *is* the spinner state; back/forward sync uses React's documented "adjust state during render" pattern |
| `assign-dialog.tsx` and `create-organization-dialog.tsx` - close on success | Extracted a `useDialogState(state)` hook that decides during render by comparing against the last `useActionState` object seen (identity comparison, so two successes in a row both close) |

### Vitest could not load its config on Node 20

```
Error [ERR_REQUIRE_ESM]: require() of ES Module .../std-env/dist/index.mjs not supported
    at .../vitest/dist/config.cjs:4:14
```

Vitest 4 loaded `vitest.config.ts` through CJS. Renamed it to
**`vitest.config.mts`**, which forces ESM loading. No dependency changes needed.

## Phase 6 - What the tests caught

Writing tests was not ceremony; two things came out of it.

1. **A real bug.** `emailSchema` was `z.email().max(255).transform(trim+lowercase)`
   — validation ran *before* normalisation, so `" ME@Example.com "` was rejected
   as invalid. Browser autofill and copy-paste produce exactly that. Fixed by
   normalising first and piping into `z.email()`. This would have shown up as
   "incorrect email or password" on a perfectly valid login.
2. **A wrong test, not wrong code.** I asserted that searching `"BERG"` returns
   only `Sofia Bergström`. It also returns `Maria Sandberg`, because `berg` is a
   substring of `Sandberg`. Partial-match-anywhere is the intended behaviour, so
   the assertion was corrected to expect both - and the test is now a better
   description of the feature.

Final: **53 tests passing**, `eslint` clean, `tsc --noEmit` clean, `next build`
clean.

## Phase 7 - Connecting to a real Supabase project

This phase was by far the most productive: four problems that nothing local
could have surfaced.

### 1. Supabase's direct database host is IPv6-only

`npm run db:push` failed with `getaddrinfo ENOTFOUND db.<ref>.supabase.co`.
DNS showed the cause: the host has an `AAAA` record and **no `A` record**, and
this machine has no routable IPv6 address.

Rather than guess the pooler region, I pulled the project's IPv6 address out of
DNS and matched it against AWS's published `ip-ranges.json`, which placed it in
`eu-north-1`. The IPv4 session pooler
(`aws-0-eu-north-1.pooler.supabase.com:5432`) then connected first try.
`db-push.ts` now detects `ENOTFOUND`/`ENETUNREACH` and prints the pooler
instructions instead of a raw DNS error.

### 2. A missing unique constraint, caught on the first real migration

Migration 003 failed:

```
there is no unique constraint matching given keys for referenced table "applications"
```

`candidate_assessments` references `applications (organization_id, id)`, but I
had only added `unique (organization_id, id)` to `jobs` and `candidates` - not
to `applications`. A genuine schema bug that no amount of local type-checking
would have found.

Fixing it exposed a second-order problem: the `drop constraint if exists` +
`add constraint` idiom I had used to make those statements idempotent **cannot**
work here, because those constraints are *referenced* by the composite foreign
keys, so the drop fails with "other objects depend on it" on any re-run. They
are now added through `tf_add_unique_if_absent()`, which checks `pg_constraint`
first. `db:push --force` proves the migrations are genuinely repeatable.

### 3. `public.schema_migrations` was world-readable

`db-push.ts` creates its own bookkeeping table, and its RLS report immediately
flagged it: RLS `false`, 0 policies. It lives in `public`, which Supabase
exposes through PostgREST and grants to `anon`/`authenticated` by default - so
anyone could have listed our migration filenames. It now has RLS enabled with
no policies at all (deny-by-default for every client) and the grants revoked.
A minor disclosure, but it was found because the tooling reports reality
instead of assuming success, which is the whole point of writing it that way.

### 4. Node 20 cannot run `@supabase/supabase-js` at all

`create-admin` died with:

```
Node.js detected but native WebSocket not found.
```

`@supabase/supabase-js` v2.109 requires a native `WebSocket`, which arrived in
Node 22. This machine had Node 20.13.1, so **every** Supabase call failed - the
scripts *and* local `npm run dev`. The earlier builds only succeeded because no
client is constructed at module scope.

A `winget` install of Node LTS stalled (most likely on a UAC prompt), so I
downloaded the official Node 22.23.3 zip into a temp directory and ran
everything with that binary - no elevation, no change to the machine's
installed Node. Now documented as a hard requirement in the README. Vercel
already defaults to Node 22.

## Phase 8 - Verifying against the live database

Three scripts, written because "the policies look right" is not verification.

**`verify-schema`** - 24 assertions in one rolled-back transaction, connecting
as the table owner (RLS deliberately bypassed; this is about the schema).
Two assertions failed on the first run and **both were my test's fault, not the
schema's**:

1. The "application stamped with a third organization's id" case reused a
   candidate/job pair that already had an application, so the *unique*
   constraint fired first (`23505`) and the composite foreign key was never
   exercised. Fixed by using a fresh pair - it now correctly fails with
   `23503`.
2. The `updated_at` check asserted the timestamp advanced. `now()` is the
   *transaction* start time in PostgreSQL, so it does not move inside a single
   transaction. It now asserts what actually matters: that the stored value is
   `now()` and not the `1999-01-01` the client tried to write.

Final: **24/24**.

**`verify-isolation`** - signs in as a seeded customer from each tenant with the
anon key and tries to cross the boundary. **21/21**. The `organization_id`
spoofing insert is rejected with `42501`, which is the RLS `WITH CHECK`
violation - exactly the clause that exists for it.

**`verify-app`** - the same question asked of the *product* rather than the
database: real session cookies replayed on plain `fetch`es, so every request
goes through proxy -> layout guard -> Server Component -> RLS. **37/37**,
including the full write journey (create job -> create candidate -> assign ->
move stage -> appears on the Kanban -> found by search -> delete).

### The one thing I could not fix properly

Five of those app checks failed at first: `/admin/*` as a customer, and
cross-tenant detail URLs, all returned **200** where I expected 307 and 404.

Before assuming the worst I dumped the response bodies. No leak: none of them
contained the other tenant's job title, candidate name or organization name.
The cause is streaming SSR - `notFound()` and `redirect()` were raised after the
shell had been flushed, so Next could not change the status and degraded to a
200 carrying the not-found UI (or a client-side meta-refresh).

I tried resolving the record in `generateMetadata`, on the theory that metadata
resolves before the shell is flushed. **It did not work** - metadata resolves
alongside the `(app)` layout, which is already awaiting the session. I kept that
change anyway, because it gives the browser tab the job or candidate name and
`React.cache()` means it costs no extra query, but I corrected the comments so
they do not claim a fix that did not happen.

What did work: moving the admin check into `proxy.ts`, which runs before
anything renders, giving a real **307**. That costs one primary-key lookup, and
only on `/admin/*`.

For the cross-tenant 404 I stopped. The honest position is in README's "Known
limitations": the status code is wrong, the body is correct and verified to leak
nothing, and the real fix is to resolve the record above the streaming
boundary. I changed the test to assert what matters - the not-found copy is
present and the other tenant's data is absent - rather than loosening it to
hide the problem.

## Phase 9 - Other findings from probing the running app

- **`lib/supabase/client.ts` had no importers.** Sign-in is a server action and
  every mutation is a server action, so no client component ever needs a
  Supabase client. Deleted it. A good side effect: the anon key is now in *no*
  client chunk at all, because nothing in client code references it - verified
  by grepping every served JS chunk.
- **API routes were redirecting instead of returning JSON.** Probing the running
  production server showed `POST /api/admin/users` answering `307 -> /login`.
  The route handlers return a proper 401, but the proxy never let them run, so
  a `fetch()` caller got an HTML page and failed at `response.json()` -
  surfacing in the AI panel as "could not reach the service". The proxy now
  refreshes the session for `/api/*` and then steps aside.
- **The client bundle had placeholder Supabase values baked in.**
  `NEXT_PUBLIC_*` variables are inlined at *build* time, and the first build ran
  against the placeholder `.env.local`. Rebuilt once the real values were in
  place. Worth remembering for Vercel: changing those env vars needs a
  redeploy, not just a restart.
